## Context

Stash has no subtitle database. There are only open feature requests
(stashapp/stash#495, #4050, #6312, CommunityScripts#405) and no prior art —
the space is genuinely empty. Meanwhile the two halves of the problem are
already solved in sibling repos: `stash-subs` generates subtitles with
structured provenance, and `StashJanitor` matches loose subtitle files to
scenes with a scoring function validated against 1,432 real subtitles. What is
missing is the part that lets one person's subtitle reach another person's
library.

moansubs is that missing piece: a self-hostable Go + Postgres service that
stores subtitle tracks keyed by video fingerprints, plus a Stash plugin that
searches, downloads, and uploads from the scene page.

Two facts make this cheap to build. Stash's `oshash` is byte-for-byte the
OpenSubtitles `moviehash` (size + uint64 sum of first/last 64 KiB, `%016x`)
and is computed by default — so the primary lookup key costs nothing and is
format-compatible with OpenSubtitles for free. And `phash` is a 64-bit DCT hash, which means
indexed Hamming search is a solved problem.

## Data model

The naive model (`hash → subtitle`) breaks immediately, for a reason specific to
how Stash computes phash: the perceptual hash is built from 25 frames sampled
across the middle 90% of the video, so **the sampling grid is positioned by
duration**. A differently-cut release of the same scene produces a completely
different phash, not a near one. Separately, `oshash` matches only
byte-identical files, and a subtitle timed against release A is seconds out of
sync on release B.

So there are three levels:

```
Work          the logical scene — what a human means by "this video"
 └─ Release   one encode: a fingerprint set + duration
     └─ SubtitleTrack   text, language, provenance, uploader
```

- **Release** carries `oshash` (`char(16)`), `phash` (`bigint`, nullable),
  `md5` (`char(32)`, nullable), `duration_ms`, plus resolution/codec hints.
- **SubtitleTrack** attaches to a Release. Serving it against a *different*
  Release of the same Work is allowed but flagged. Sync offsets live in a
  `(track, release) → offset_ms` cross-reference table, not on the track —
  the same track served against two other releases needs two different
  offsets.
- **Work** is inferred, not authoritative: releases group into a work by
  phash proximity, duration, and title/code tokens. Keep it advisory in v1 —
  a wrong grouping must never lose a subtitle.

Two hash-handling rules that will silently corrupt the database if missed:

1. **Zero-pad phash to 16 hex chars on ingest.** Stash's `Fingerprint.Value()`
   uses `strconv.FormatUint` with no padding, so a hash with leading zero bits
   arrives as fewer than 16 characters. `oshash` is always padded; `phash` is
   not. Two conventions on the same `value: String!` field. Never compare phash
   as a string — parse to `uint64` and compare with `popcount(a ^ b)`.
2. **Store phash as signed `bigint`**, matching how Stash stores it in SQLite
   (the `uint64` bit pattern reinterpreted), and reinterpret on read.

Schema sketch — names indicative, exact DDL is the implementer's call, but
every column here exists for a reason stated somewhere in this file:

```
works(id, title, code, created_at)                 -- advisory grouping only
releases(id, work_id NULL, oshash char(16) NOT NULL,
         phash bigint NULL,
         phash_b0..phash_b4 int2 NULL,             -- MIH blocks, defined under Lookup
         md5 char(32) NULL, duration_ms bigint NOT NULL,
         width, height, video_codec, created_at)
subtitle_tracks(id, release_id, lang text,         -- full BCP-47 as uploaded, e.g. pt-BR
         body text,                                -- normalized SRT, re-rendered on ingest
         generated bool NOT NULL,
         provenance jsonb NULL,                    -- parsed stash-subs marker
         license text NOT NULL DEFAULT 'CC0',
         source text NULL,                         -- permission-mirrored seeds
         uploader_id, created_at)
track_release_offsets(track_id, release_id, offset_ms,
         PRIMARY KEY (track_id, release_id))
accounts(id, name, token_hash, disabled, created_at)
```

## Lookup: bucketed by default

StashDB already receives phash/oshash/md5 from user libraries via
`submitStashBoxFingerprints`, so hash submission is an accepted norm in this
ecosystem. The difference is that submission is a deliberate batch, while
subtitle lookup fires continuously as you browse — leaking a timestamped
browsing trace rather than a one-time inventory. That is worth designing
around, and it turns out to be nearly free:

- **oshash** — client sends the first 5 hex chars. Server returns every
  release in that bucket. Client filters locally.
- **phash** — **multi-index hashing**. Split the 64 bits into 5 blocks of ~13
  bits. By pigeonhole, any two hashes within Hamming distance 4 must share at
  least one block exactly. The client queries by block value, gets the bucket,
  and computes true Hamming distances locally. This is *exact* for d≤4, not an
  approximation. **Honesty note:** full recall requires querying all 5 blocks,
  and a server that correlates those five requests reconstructs the full hash —
  so MIH is the lookup *mechanism* (exact d≤4 on plain btree indexes), not a
  privacy guarantee. The real k-anonymity is the oshash prefix; document phash
  lookup as trusting the node.
- **Full-hash mode** stays available behind a setting, for d≤8 fuzzy search.
  Never exceed 8 — stash-box warns explicitly and false positives climb
  sharply. POST, not GET, so hashes stay out of access logs.

Server-side there is no Hamming extension: MIH block columns are btree
indexes, and the rare fuzzy query filters a bucket with
`bit_count((phash # $1)::bit(64))` (Postgres 14+). At this database's scale
that is effectively free; `pg-spgist_hamming` would require a custom Postgres
image and only becomes interesting at millions of releases.

**Bucket definitions are part of the API contract** — client and server must
agree bit-for-bit, so they are fixed here, not left to the implementer:

- oshash prefix = the first 5 characters of the 16-char zero-padded lowercase
  hex string.
- phash blocks, with phash as `uint64`: `b0` = bits 63–51, `b1` = 50–38,
  `b2` = 37–25, `b3` = 24–12 (13 bits each), `b4` = bits 11–0 (12 bits).
  Extract with shift-and-mask; store each block in its own indexed column.

Endpoints roughly:

```
GET  /api/v1/lookup/oshash/{prefix}      -> releases in bucket
GET  /api/v1/lookup/phash/{block}/{val}  -> releases in bucket
POST /api/v1/lookup/batch                -> many buckets at once (SceneCard badges)
POST /api/v1/lookup/exact                -> full-hash mode, opt-in
GET  /api/v1/subtitles/{id}              -> track text + provenance
POST /api/v1/subtitles                   -> upload (account token required)
```

## Matching

Hash matching alone fails for a majority of real libraries: **phash is opt-in
in Stash and frequently absent**, and oshash only ever matches identical files.
The fallback is the scoring cascade `StashJanitor` already implements.

Confidence order:

1. `oshash` exact — identical file. Confidence 1.0.
2. `md5` exact — same, usually absent. Bonus index only.
3. `phash` Hamming ≤4 **gated by `|Δduration| ≤ ~1s`** — same content, different
   encode. High confidence.
4. `phash` Hamming 5–8 + close duration — offer, never auto-apply.
5. No phash: fall through to the token/code/runtime scorer. **(v2)**

v1 serves levels 1–4 only. Across strangers' libraries oshash almost never
matches — it requires byte-identical files — so **phash-within-4 gated by
duration is the workhorse**, and phash generation is opt-in in Stash. The
plugin README and setup flow must tell users to enable it.

**Port `StashJanitor/internal/subs` rather than reimplementing.** Same author,
same license, already Go. Split across versions: v1 needs `runtime.go` and
`lang.go` (upload-time runtime sanity check and language detection); the token
scorer (`match.go`, `normalize.go`, `vocab.go`) is the no-phash fallback and
lands in v2. Directly reusable:

- `runtime.go` — `Runtime()` (last-cue timestamp from an SRT/VTT stream) and
  `RuntimeFit()` (the ±20s / 60s / 180s tolerance curve). This is the signal
  that makes matching trustworthy.
- `normalize.go` — `Tokens`, `Codes` (studio/JAV code extraction), `F1`,
  `normKey`.
- `vocab.go` — creator-vs-content token splitting.
- `lang.go` — language detection from subtitle text.
- `match.go` — the additive scorer (code +60, exact stem +100, title F1 +0..70,
  runtime +0..45 or −30, date +25) and `decide()`'s verdict rules.

`match.go`'s comments encode two lessons worth preserving verbatim on the
server side: title and filename must be scored *separately* and the better one
wins (52% of scenes in a measured 61k library had no title at all), and runtime
alone is never identification — a weak name plus a lucky duration produced a
tail of confident-looking nonsense.

The server-side adaptation is that it scores subtitle-vs-*release* across many
users' encodes, not subtitle-vs-local-library, so `SceneRef` becomes a release
record and the `Index` needs to work against Postgres rather than an in-memory
slice.

## AI-generated disclosure

Do not rely on self-declaration. `stash-subs` already emits detectable
provenance, so the server can determine this itself on ingest:

- `subtitles.py:looks_generated()` sniffs the `[stash-subs]` marker from the
  head and tail of the file (4 KiB each end).
- The VTT `NOTE` block carries the full `Provenance` JSON — tool, version,
  `asr_model`, `mt_model`, source and target language, date.
- `<subtitle>.stash-subs.json` carries the same when written as a sidecar.

Port `looks_generated` and the `Provenance` field set to Go. On upload: parse
the marker, ingest structured provenance into columns, set `generated: true`
regardless of what the uploader claimed. Store the distinction between
*transcribed* (ASR only) and *translated* (ASR + MT) — a machine translation of
a machine transcription is materially worse than either, and `Provenance`
already distinguishes them via `src`/`dst`/`mt_model`.

Surface it at **download** time in the plugin UI — a badge and a one-line
explanation, not a blocking dialog. Also strip the marker cue on serve if the
user opts out of it, via the existing `without_marker()` logic.

## The Stash plugin

One plugin directory, one `.yml`, two halves.

**Exec half** — a static Go binary (ship `linux/amd64` + `arm64`; avoids
depending on Python or `stashapp-tools` being present in the user's Stash
container). Stash writes JSON to stdin containing `server_connection` with a
session cookie; the plugin reconstructs `http://host:port/graphql`. Progress and
logs go to **stderr** with the `\x01i` / `\x01e` / `\x01p` control prefixes.

Use `interface: rpc` rather than `raw` — `raw` tasks are killed with no signal,
and a library-wide scan needs to stop gracefully. Take an **API key as a plugin
setting** rather than relying on the session cookie, which expires mid-run on
long tasks (stashapp/stash#5332).

**UI half** — `PluginApi.patch.after("ScenePage", ...)` for a "Find subtitles"
panel, `patch.after("SceneCard", ...)` for a has-subs badge. Outbound `fetch` to
the moansubs server is CSP-blocked unless declared in the manifest:

```yaml
ui:
  javascript: [moansubs.js]
  csp:
    connect-src: ["https://your-node.example"]
```

Because the server address is user-configurable but the CSP is baked into the
manifest, the UI half should call the exec half via `runPluginOperation` — which runs an
RPC plugin operation synchronously and returns its output, unlike
`runPluginTask`, which only enqueues a job and returns an ID — rather than
fetching the moansubs API directly. That keeps the network egress in the
process that has no CSP. Probe for `runPluginOperation` at startup like any
other uncertain schema field.

### Delivery constraints that fail *silently*

All three are already documented in `stash-subs/CLAUDE.md` and each one produces
a written file, an empty player, and nothing in any log:

1. **The language suffix must be a bare ISO 639 subtag.** Stash parses it with
   x/text's `language.ParseBase()`. `.pt-BR.srt` does not parse, so Stash treats
   `pt-BR` as part of the filename and the caption never attaches. Port
   `langs.py:is_caption_suffix` / `normalize` (or reuse
   `StashJanitor/internal/subs/lang.go`). Consequence for the schema: moansubs
   may store `pt-BR` internally, but the filename written to disk loses the
   region, and two Portuguese variants cannot coexist as sidecars.
2. **`.srt` and `.vtt` only.** A suffix-less caption is filed as `"00"`, a
   deliberately invalid ISO 639-1 value that must never compare equal to a real
   code.
3. **Captions are read-only in GraphQL** — no field in `SceneUpdateInput`, no
   `captionCreate`. The only way to add one is to write the sidecar and trigger
   `metadataScan` on the Stash-side path (not the plugin's mapped path). Only
   needed for a genuinely new (language, extension) pair.

Write **SRT**. Stash converts everything to WebVTT on the fly at
`GET /scene/{id}/caption?lang=&type=` anyway, so VTT's only real advantage is
the `NOTE` block for provenance — worth using when provenance matters.

One more, from the same file: **an unknown GraphQL field fails the entire
query**, and Stash's schema shifts between releases. Any field whose presence is
uncertain needs a startup capability probe with fallback — see
`stash_subs/stash.py:Client.probe_captions` for the pattern.

## Upload safety

Subtitle files are attacker-controlled text rendered in a browser.

- Cap file size and cue count; reject anything absurd.
- Accept only SRT and VTT; parse and **re-render** rather than storing raw
  bytes. `subtitles.py:parse()` anchors on the timestamp line and ignores cue
  numbers, headers and NOTE blocks — the same approach in Go gives sanitization
  for free, since anything unparsed is discarded.
- Normalize to UTF-8; strip HTML-ish markup beyond the basic `<i>`/`<b>` tags.
- Rate-limit uploads per account token, and anonymous downloads/lookups per IP
  so a scraper cannot flatten the node (dumps exist for bulk access — point
  scrapers there).
- No self-registration in v1. Accounts are created by an admin CLI command
  (`moansubs account create <name>`) that prints a random 256-bit hex token
  exactly once; the server stores only the token's SHA-256 in
  `accounts.token_hash`.

## Cold start

An empty subtitle database is worthless, and the obvious seed — bulk-uploading
`stash-subs` output — would flood it with machine-generated content on day one.

Resolved as follows:

- The author operates the canonical public instance from launch and seeds it
  with a few hundred human-matched subtitles from their own library.
- **Outreach to existing JAV subtitle publishers** for permission to mirror
  their work, credited via the uploader and provenance fields. These tracks
  are not CC0 — record the actual grant per track (`license`/`source`
  columns) and don't pretend otherwise.
- Machine-generated uploads stay opt-in and explicit: a `moansubs push` task

  after a successful run. Because provenance is auto-detected, generated
  tracks are correctly labeled from the start, and search ranks human-written
  tracks above machine ones by default. That makes a generated-heavy early
  database acceptable rather than poisonous.
- Publish periodic dumps so third-party nodes never start empty and the
  canonical node stays replaceable.

## Known-hard cases to acknowledge, not solve in v1

- **Censored vs uncensored JAV releases** of the same work: different duration,
  different phash, sometimes different runtime. Only code/token matching
  reaches these. Very common in this space.
- **Compilations** containing a scene that also exists standalone.
- **Hardcoded subtitles** already burnt into the video — undetectable from
  metadata; a user will upload a redundant track.
- **Sync drift** across releases. v1 warns; an offset-adjustment UI comes later.

## Model delegation

Guidance for whoever orchestrates this across models/agents. The rule: the
cost of a model should match the *ambiguity* of the work, not its size.
Well-specified work with tests named in this file is safe for a mid-tier
model; work that fights undocumented external behavior is not. Tier names
below map to the current Claude lineup (strong = Fable/Opus, mid = Sonnet,
small = Haiku) but the shapes outlast the names.

| Work | Tier | Why |
|---|---|---|
| Repo scaffolding: LICENSE, Makefile, CI workflows, Dockerfile, compose file — copied from siblings | small–mid | Mechanical transcription of existing conventions; the sibling repos are the spec. |
| Step 1 — schema, migrations, hash padding/round-trip, MIH blocks | mid | Fully pinned above (bit ranges, columns, test vectors). Subtle but specified. |
| Step 2 — accounts, upload endpoint, parse/re-render, marker sniffing | mid | Python→Go port with the source as spec; tests come across. |
| Step 3 — lookup API, rate limits | mid | Contract is fixed in the Lookup section. |
| Step 4 — plugin exec half | **strong** | Fights the three silent-failure modes and Stash schema drift; failure produces no error anywhere. Needs judgment, not throughput. |
| Step 5 — plugin UI half | **strong** | `PluginApi.patch` internals are undocumented and version-dependent; expect experimentation against a live Stash. |
| Step 6 — upload path, `stash-subs` hook, seeding | mid | Composes already-built parts. |
| Step 7 (v2) — token scorer port | mid, strong for the Postgres `Index` adaptation | The port is mechanical (tests unchanged, regression corpus as gate); rethinking `Index` against Postgres is design work. |
| Review gates: after step 1, after step 4, before seeding the public node | **strong** | Step 1 is where silent corruption lives; step 4 is where silent failure lives; seeding is the first irreversible public act. |

Two rules regardless of tier: any model doing a port reads the source being
ported first, and no model marks a step done whose named tests haven't run.

## Verification

- **Unit:** ported `internal/subs` tests must pass unmodified. Hash padding and
  signed round-trip tested against real Stash fingerprint values, including a
  phash with leading zero bits (the unpadded case). If no live Stash is
  reachable, self-generate vectors: implement oshash from the upstream file in
  the Reference section and hash synthetic files; for the unpadded case, take
  a `uint64` with high zero bits (e.g. `0x00ffabcd12345678`), format it with
  `strconv.FormatUint(x, 16)` as Stash does, and assert ingest zero-pads it
  back. Ask the user for real values from their Stash when available — the
  self-generated vectors supplement, not replace, that check.
- **Multi-index hashing correctness:** property test — for random 64-bit pairs
  within Hamming distance ≤4, assert at least one of the 5 blocks matches
  exactly. This is the load-bearing correctness claim of the bucketed lookup —
  if it fails, the default lookup silently misses matches.
- **Matcher regression (v2, with the scorer port):** replay
  `../subtitle-match-report.md` (54 orphaned subtitles, 33 CONFIRMED /
  16 LIKELY / 5 AMBIGUOUS) through the ported scorer and assert the verdict
  distribution is unchanged. This is a real-library regression corpus and
  should be preserved as one.
- **Integration:** `docker compose up` (stock Postgres image), upload a
  subtitle, look it up by prefix from a second client, confirm the full oshash
  never appears in server request logs.
- **End-to-end against real Stash** *(requires the user: a live Stash instance
  and a human to confirm the caption renders in the player — ask, don't skip
  or simulate)*: install the plugin, run search on a scene, download, confirm
  the caption actually appears in the player. This is the only test that
  catches the three silent-failure modes. Explicitly include a case with a
  regional language code (`pt-BR`) and assert the plugin refuses it with a
  clear message rather than writing a file that never attaches.
